# 実例 03: 厳格な JSON 出力制約

APIレスポンスから前置き、Markdownのバッククォート、挨拶、不要なおしゃべりを完全に排除する制約例です。

[English](03_strict_json_api.md) | [日本語]

---

## 自然言語による指示例（約80トークン）
> 「パース可能な純粋なJSONのみで応答してください。前置きの挨拶、解説、Markdownのコードブロック（```json）は一切含めないでください。スキーマが厳密に有効であることを確認してください。」

---

## Φ_Lang による記述 (v3.3.1)

```text
[ phi:v3.3.1 | mode:filter | out:json ]
@Constraint chat=ban markdown_fence=strip schema="strict_json"
@Pipe in=Raw -> validate:json -> Out

```

---

## 期待されたモデルの振る舞い（設計時の仮説）

モデルは前置き挨拶を削り、コードフェンス（バッククォート）の出力を抑制し、内部でJSONオブジェクト構造を検証した上で、生のJSON文字だけを出力バッファに直接出力する。

### 実際に発生した問題（破綻の要因）

上記のような「プロンプトによる無茶ぶりな完全封殺」は、多くのモデルで構文エラーや出力停止（空応答・パース失敗）を引き起こします。

1. **「思考・自己検証」と「1文字目からの即時出力」の自己矛盾**
「スキーマが厳密に有効であることを確認せよ」という指示を実行するには、モデルには生成前の思考やバッファ（トークンを生成しながら検証する余白）が必要です。しかし同時に「前置きやフェンスを一切禁止し、1文字目から `{` を出せ」と課すと、モデル内部の予測が衝突し、構文崩れを起こしやすくなります。
2. **LLMの学習分布とコードフェンスのバイアス**
LLMはプログラムやAPIではなく、あくまで「次のトークンを確率的に予測する」モデルです。大量の学習データ（Markdownや技術文書）において、JSONは「```json」で囲まれて出現する確率が圧倒的に高いため、プロンプトで無理やり「フェンス禁止」を命じると、トークン生成の確信度が落ちて出力が不安定になります。
3. **低レイヤー（バッファ・ストリップ）制御の不可能性**
LLM自身は「メモリ上の出力バッファを直接操作する」「後から文字を剥ぎ取る（strip）」といったパイプライン処理の実行環境を持っていません。`@Pipe` のようなメタ指示をモデル単体に求めても、実体としては単なる「制約の多いテキスト指示」として解釈されるため、物理的なバッファ制御には繋がりません。

## Φ_Lang による改訂版記述 (v3.3.2)

LLM には「開始文字の明示」と「スキーマ構造」を与え、コードブロックの有無に関わらず安全に処理できる記述にアップデートします。

```text
[ phi:v3.3.2 | mode:transform | out:json ]
@Schema target={"status": string, "result": any}
@Constraint prefix="{" suffix="}" explain=ban markdown=ban
@Pipe in=Raw -> Out

```

---

## 改訂版で期待される振る舞い

モデルは挨拶や解説を挟まず、指定されたスキーマに従って `{` から始まる JSON 文字列を安定して生成します。

## 実務におけるベストプラクティス（コパイロットメモ）

プロンプト単体で 100% の生 JSON を保証しようとするのはアンチパターンです。現場では以下のいずれかを組み合わせます。

1. **API パラメータの活用（最優先）**
* OpenAI / LocalLLM: `response_format={"type": "json_object"}` または 文法拘束（GBNF）
* Gemini: `response_schema` / `response_mime_type="application/json"`


2. **ホスト側（Python等）での軽量サニタイズ**
* モデルが万が一 ` ```json ` フェンスを出力した場合でも、受信用プログラム側で正規表現等により外枠を除去して `json.loads()` に渡す設計が最も堅牢です。
